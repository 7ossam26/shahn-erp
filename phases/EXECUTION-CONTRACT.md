# Shared execution contract

Authority: PLAN-001 approved for phase authoring in session025, ERP-D-205 / ERP-R-214. Each numbered Markdown file is a complete prompt for one later implementation result. This file defines the shared handoff conventions; it does not authorize running all phases in one turn.

## Starting a phase

Read the selected phase, the master plan, its named specification sections and this contract. Inspect the actual workspace and relevant instructions before edits. Planning paths are desired outputs, not claims that code exists. Preserve existing owner changes and `ui-preview/`. The prototype's fixtures and routing never become backend authority. Do not initialize a remote, publish a deployment, commit unrelated files or modify Tawsel as a side effect. The phase commit and push below are explicitly authorized.

Check prerequisites by running/inspecting their stated evidence. A status label or an old screenshot is insufficient. A small missing export, migration registration or seed adaptation may be repaired inside scope and recorded; a missing issuer, canonical extension, actual prior subsystem or unsafe migration is a material dependency. Record its owner, exact observed failure and affected cases. Continue independent work, but do not call the blocked outcome complete or ask the owner to repeat settled product discovery.

Every future agent may resolve ordinary implementation details inside the specified architecture. It may not invent commercial behavior, substitute an unsupported Tawsel call, weaken an invariant or silently drop a selected journey. Where two source instructions conflict, the latest decision governs ERP policy; the pinned public contract governs current Tawsel capability.

## Git workflow: main, phase commit and push

Owner instruction, 2026-10-05: this workflow applies to every selected plan/phase and supersedes earlier branch habits and historical statements that commit/push was not authorized.

1. Work directly on `main` in the existing checkout. Do not create a branch or worktree. Run phases sequentially so their edits and verification do not overlap. Inspect `git status --short --branch`, the current branch, starting HEAD and existing remote before editing; record pre-existing changes. If on another branch, switch to the existing `main` only when doing so preserves all work and required prerequisites. If safe switching is blocked or needed work exists only on another branch, report the exact blocker; do not reset, discard, stash or merge unrelated work automatically.
2. Fetch the existing `origin` and inspect `main` versus `origin/main`. On a clean checkout, update a behind-only `main` with `git merge --ff-only origin/main` before implementation. Do not rewrite divergent history or push pre-existing unpublished commits without establishing that they belong to the authorized work. A missing remote, authentication failure or unsafe synchronization is a Git blocker to report, not permission to create another branch or remote.
3. Implement only the selected phase and record its actual evidence and handoff. Before committing, pass `npm run lint`, `npm run typecheck`, `npm run build`, `npm run test:phase -- Pxx` with the actual phase ID, and the phase's other required acceptance/regression checks. Inspect the final diff and run `git diff --check`. Fix in-scope problems and rerun affected checks. A required failing, skipped, unavailable or blocked acceptance gate prevents the completion commit and push, even when local subsets pass. Preserve work on `main`, record the truthful status and report the blocker. Do not weaken a gate to obtain a passing result.
4. When all required gates pass, stage only the selected phase's implementation, necessary in-scope fixes and updated evidence/status/handoff files. Inspect the staged diff and run `git diff --cached --check`; exclude secrets, generated build output and unrelated owner edits. Commit with the phase number and a short result, for example `git commit -m "phase 14: implement returns and redispatch"` for P14. Do not create an empty or fabricated completion commit. The owner's instruction is standing authorization for this commit and push; no repeated approval question is required.
5. Push with `git push origin main` and verify the remote `main` contains the resulting commit. Never force-push. If the remote advances, fetch and inspect it; reconcile only authorized changes without overwriting others and rerun checks affected by the changed base before retrying. If push is blocked by conflicts, authentication or branch protection, keep the local commit and report its hash and exact failure; do not create a workaround branch/PR or claim it was pushed.
6. Report the phase result, required check outcomes, commit hash and verified push result in the final handoff. The commit includes the pre-commit execution evidence; report its final hash/push result in chat without creating a recursive bookkeeping commit. Stop after this phase. A Git push does not authorize deployment or starting the next phase.

## Common interface and commands established by P01–P03

P01 establishes Node24 LTS/npm workspaces and these root entry points: `npm ci`, `npm run dev`, `npm run lint`, `npm run typecheck`, `npm run build`, `npm run test:unit`, `npm run test:db`, `npm run test:browser`, `npm run test:phase -- P01`, `npm run db:migrate`, `npm run db:status`, and `npm run seed:dev`. Later phases register their own `Pxx` suite in `test:phase`. Until that phase is implemented, an unknown/unregistered suite must fail explicitly; zero matching tests is not success. The runner reports which unit, database, public-integration and browser suites actually ran and propagates failure. It never manufactures missing services or silently converts integration tests into mocks.

Development/test seeds are isolated, repeatable and identified by a test company/batch. Refuse to seed a production environment. Future prompts may add narrower commands when useful; document their exact invocation and actual result. Do not run destructive cleanup against an unverified database/host.

P02 owns `AccessContext` with authenticated principal, company, current screen grants, assigned branches and authorization revision. P03 owns `UnitOfWork` with one checked-out `pg` client, `commandId`/canonical payload identity, `expectedVersion`, stable command-result lookup, immutable audit/source identities and journal posting. Later modules join this local transaction through explicit service interfaces. They do not open nested independent transactions for effects that must commit together.

Native `Money` uses EGP and integer-string `amountMinor`; SQL uses bigint. Native UUIDs and digits-only display references are distinct. Canonical Tawsel `Money`, `actionId`, revisions, headers, signatures and host authority remain exact. P11 supplies the canonical adapter, signed receiver and source outbox; public network effects occur after local commit with durable recovery. No distributed-transaction claim, shared database or driver impersonation is allowed.

Each HTTP module writes closed request/response schemas and current OpenAPI under `packages/contracts/`, including validation/error cases. Runtime output paths below are implementation targets. Pin supported dependency versions during P01 and record any later justified change in the version manifest; do not silently upgrade the entire stack in a business phase.
