# P05 stock consumer interface

Migration `0009_p05_products_stock` is additive after P04's `0008`. The planned `0005` name was adapted because the real registry already occupies 0005–0008. Existing migration bytes and `ui-preview/` are preserved. Upgrade creates no stock, fictional receipts, journal effects or company valuation.

`packages/contracts/src/inventory/index.ts` exports closed runtime schemas, TypeScript client contracts and current native OpenAPI. Units are whole pieces, safe JSON integers (0–9007199254740991); actual receipt inputs start at 1. SQL stores `bigint`. Domain arithmetic checks each addition including sound+unavailable and combined claims. Display names and option descriptions never bind identities. Product edits include `expectedVersion`; all old variants must remain, optionally inactive. Newly added variants have generated identities. Historical receipt labels remain snapshots after rename.

`inventoryCommands(pool)` registers only `product.create`, `product.update` and `stock.receive` with P03. Families are `inventory.product` and `inventory.receipt`, scoped by company/principal/family/command ID. Current inventory grant and assigned receiving branch are checked before replay, compacted result recovery or detail/history read. Receipt confirmation is a staff assertion of physical arrival. Actual date may be past; recorded time is current UTC. Future Cairo dates reject. No receipt editing/deleting endpoint exists.

Caller-owned stock interfaces are in `apps/api/src/modules/inventory/service.ts` and `packages/database/src/inventory/index.ts`:

- `StockPositionRepository.lock(client,company,keys)` deduplicates and sorts branch/brand/variant keys, upserts an absent zero position through the unique key, then locks it. It opens no transaction. Callers must already own the P03 transaction and register the full sorted key set using `uow.lockOrder('stock',positionKey(key))` before any cross-module stock effects. Configuration/aggregate locks precede stock locks. No external HTTP runs inside the transaction.
- `reserveStock(uow,key,input)` requires the stock lock and current assigned branch. Its source is a registered `stock_source` kind `order` or `loose_transfer`; the caller owns the real aggregate/source relationship, state, version, audit and command. It checks current available stock, combined safe-integer claims and writes the reservation plus immutable event. It does not create an order or transfer. P07/P15 own those workflows.
- `releaseStockReservation(uow,key,reservationId,sourceId)` closes the claim once and retains a release event. P07/P15 must validate a legitimate release/cancellation state before calling; this is not a post-handover cancellation endpoint.
- `changeStockCondition(uow,key,input)` checks expected position version, preserves physical total, appends one source/effect identity and updates sound/unavailable. Repeated exact source effect has no additional effect; a changed effect conflicts. P21 owns actual inspection evidence, reasons, authorization/audit and the correction UI. This interface exposes no ordinary adjustment screen.
- `StockPositionRepository.update` persists checked quantities and recalculates shortage holds while the position is locked. It is a lower-level repository; domain consumers must check arithmetic, append their uniquely sourced movement and audit in the same transaction. It is never a raw HTTP balance editor.

`stock_source(company,id,kind,source_system,source_identity,revision)` uniquely identifies receipt/order/loose-transfer/condition/adjustment sources. `stock_movement(company,source_id,effect_key)` and the separate unique receipt-line link prevent duplicate source effects. Same-company/brand/branch composite FKs protect positions and receipt lines. SQL receipt-effect guards require the exact received condition and deltas. Source/receipt/line/movement/revision/outcome histories reject mutation or deletion.

Equations are physical=sound+unavailable; reserved=active order+loose-transfer claims; available=max(sound−reserved,0); shortage=max(reserved−sound,0). There is deliberately no reserved≤sound constraint. `shortage_held` applies to every active claim at an affected position; replenishment/condition recovery recomputes all these holds atomically. Later handover services must check the hold under the same position lock. P05 has no actual shipment/transfer whose handover can be performed.

Read filters are parameterized, allowlisted, AND across dimensions and OR within branch/brand/category sets. Default page size is 25; 50/100 are allowed. Stable ties use product/variant names and branch/variant identities. A single SQL statement returns inventory rows and count from the same snapshot, with `asOf`. Virtual zero positions show defined variants without creating receipt rows. Movement-date filters select positions having a **recorded movement** in the inclusive Cairo date interval; balances remain current. There is no historical balance snapshot query. Detail/back carries query state, and current authorization invalidates revoked selections.

The Parcels API is an authorized empty boundary with `P06_NOT_IMPLEMENTED`, explicit branch/external custody selection and no manufactured fixtures. P06 owns real parcel facts. Stored packed components must retain their existing product allocations; the parcel view must not add a second stock total. P13/P15 own driver/carrier projections. The current user history screen renders actual receipt lines; later consumers must extend its source display for their non-receipt effects when they implement those journeys.

Reservations in tests are identified P05 model fixtures. No P07 order preparation, P14 return processing, P15 physical transfer, P21 adjustment UI, financial valuation, count engine, barcode workflow or Tawsel interaction is claimed. Native production startup has no fixture login/SQL control routes; the disposable test harness alone supplies marked company data.
