# P19 interfaces, boundaries and handoff

Native implementation dated 2026-10-07. Storage is a separate subledger: it never posts to the brand payout wallet (`kernel` family `brand`), never offsets brand eligibility, and makes no Tawsel call.

## Implemented paths

- `packages/database/migrations/0023_p19_storage.sql` (planned as `0019`; `0019`–`0022` were already used, so the next free number is applied, as P18 did): schema `storage` with `agreement` (one per company brand, original start/anchor, first billable index, active/stopped with exclusive stop boundary), immutable `agreement_revision` (fee/revenue branch effective from a period index), `credit_account` (dedicated `(company, brand)` lock row on `kernel.resource` family `storage`), `period` (half-open `[start, next_start)`, snapshotted fee/branch/revision, period-start revenue effect, job/lease/fence identity, unique index/start/source, gist exclusion on overlapping ranges), `receipt` (receipt lots with actual date, recorded time, method/account/branch, immutable result), `allocation` (receipt-lot → period amounts, trigger `payment`/`renewal`), `refund` + `refund_source`, `stop_record`. SQL function `storage.period_start(original, anchor, index)` is the original-anchor boundary used by the database guards.
- Database guards: row-locking triggers cap allocations at the period fee and cap allocations+refunds at each receipt amount (racing writers cannot over-allocate or overdraw a lot); periods must equal the deterministic boundary, be contiguous, be on/after the first billable index, start before any stop boundary and carry the applicable revision; revisions cannot reprice a generated period; agreement anchors are immutable once a period exists; deferred triggers prove each receipt/refund equals its `finance.money_movement` and typed storage effect, each allocation source equals its allocation effect, and each period equals exactly one complete `operating/storage` earning (none for a zero fee). A real storage cash movement or storage/operating-storage effect cannot commit without its storage record (P03 `fixture` resources exempt). All history tables are immutable.
- `money_movement.source_kind` gains `storage_receipt` and `storage_refund`; capability `storage` (policy `wallet`: company-wide brand view, branch-scoped money) is implemented as اشتراكات التخزين at `/storage`.
- `packages/domain/src/storage/`: `periodStart`, `periodRange`, `periodIndexOn`, `firstBillableIndex`, `changeEffectiveIndex`, `stopBoundary`, `nextDuePeriod`, `revisionFor`, `periodOutstanding`, `unallocatedCredit`, `planStorageAllocations` (oldest due date then period ID; lots by actual date then receipt ID), `planStorageRefundSources`, status/overdue helpers. Exact bigint money through the P03 helpers.
- `packages/database/src/storage/`: transaction-aware reads/locks (`readStorageAgreement`, `lockStorageAgreementRow`, `lockStorageCreditRow`, `readStorageRevisions`, `readStoragePeriods`, `readStorageLots`, `insertStorageAllocations`, `bumpStorageCreditVersion`, `storageRenewalStatus`, `storageDiscoveryCandidates`) and the P24/P21 fact queries below.
- `packages/contracts/src/storage/`: closed schemas, validators, examples and OpenAPI for the 12 storage paths (generated into `packages/contracts/openapi.json`). There is no public period-generation endpoint.
- `apps/api/src/modules/storage/`: `clock.ts` (Cairo database date; controlled clock only for isolated tests/trials), `agreements.ts` (lock helpers, brand-setup terms sync, read models), `service.ts` (`StorageService` payment/refund/stop commands, previews, recovery), `renewal.ts` (`StorageRenewalService`), `http.ts` (routes registered in `apps/api/src/app.ts`).

## Agreement terms and dates

- P04 brand setup remains the terms editor. In the same transaction as `brand.create`/`brand.update` (configuration lock → agreement aggregate lock → brand wallet/credit resources): first configuration creates the one agreement and revision 1; a fee or revenue-branch change appends a revision effective from `changeEffectiveIndex(today)` (the next period by calendar, never a generated one); the original start may change only before any period exists (`STORAGE_ANCHOR_IMMUTABLE`); removing storage is rejected (`STORAGE_AGREEMENT_RETAINED`); turning it inactive is rejected (`STORAGE_STOP_USE_STORAGE_FLOW`) because stopping is the dedicated storage action. Before migration 0023 exists the sync is a no-op (upgrade-sequence tests); readiness never serves such a schema.
- **Backdated entry / migration policy:** billing starts with the first anniversary period beginning on/after the agreement's entry date (`first_billable_index`). Earlier periods are historical and require existing evidence through the P21 opening/adjustment flow; they are never auto-generated. The 0023 carry-over uses the migration's Cairo date. A future start date bills from period 0.
- Stop records the current protected period's exclusive end (never before an already generated period's end); before service starts it is the original start, so no charge is ever earned. Stop keeps dues, allocations, credit and history; it is not a refund and does not prorate.
- The renewal worker posts one complete `operating/storage` effect per period, effective on the period start, at the snapshotted agreement branch; credit allocation in the same batch uses the period start as its effective date. Payment-triggered allocation is effective on the entry date; the receipt keeps its actual date and recorded time.

## Lock order (all storage writers)

command/source identity → storage agreement (`aggregate` key `contract-storage:<id>`, after the shared commercial configuration and before a period's `operating:<id>` resource) → storage credit account (`wallet` key `storage:<brandId>`, after `brand:<brandId>`) → receipt/period rows (SQL guard row locks) → money accounts (sorted) → append-only effects. Renewal, payment, refund, stop and terms changes all take the agreement lock first. Previews take the same locks and return `creditVersion`; a confirmation with a stale `expectedCreditVersion` is a retained `STORAGE_CREDIT_CHANGED` 409 and the UI reopens review. Renewal uses its period source identity (`storage`/`<agreement>:<index>:<start>`/`period`) instead of a browser version.

## Commands (P03 CommandService, capability `storage`)

| Kind (family) | Effects in one transaction | Retained 409 rejections |
| --- | --- | --- |
| `storage.payment.record` (`storage.payments`) | P09 deposit (`storage_receipt`) + equal storage `receipt` effect + one storage `allocation` effect when dues exist; receipt row with immutable result; allocation rows; credit version +1; audit. | `FUTURE_PAYMENT_DATE`, `STORAGE_AGREEMENT_REQUIRED`, `STORAGE_CREDIT_CHANGED`, account 409s. Account usage/branch scope failures are 403/404 with no record. |
| `storage.credit.refund` (`storage.refunds`) | P09 withdrawal (`storage_refund`) + storage `refund` effect; refund row, `refund_source` rows (oldest lots first); credit version +1. No revenue reversal, no wallet payout. | `STORAGE_CREDIT_ALLOCATED` (amount within allocated money: P21 correction first), `INSUFFICIENT_STORAGE_CREDIT`, `INSUFFICIENT_FUNDS`, `STORAGE_CREDIT_CHANGED`, `FUTURE_PAYMENT_DATE`. |
| `storage.agreement.stop` (`storage.agreements`) | Agreement `stopped` + boundary, stop record with result. Requires assignment to the current revenue branch. | `REVISION_CONFLICT` (with `currentVersion`), `STORAGE_ALREADY_STOPPED`. |

Recovery: `GET …/payments|credit-refunds|agreements/commands/{commandId}?companyId=` for the same principal with current grant and current assignment to the receiving/funding/revenue branch. Results survive command compaction through the immutable `result` columns.

## Renewal worker

`StorageRenewalService.discover()` enqueues at most the next single due period per agreement without an in-flight job (job identity `<agreement>:<index>:<start>`). `runOne()` claims one job (lease, fence), runs one transaction (lease recheck → source identity → agreement lock → revalidation → operating resource → credit lock → period, earning, allocation, credit version, audit, chained next job), then acknowledges in a separate transaction. A crash after commit is recovered as `already_generated`; an expired worker cannot write (`lease_lost`) or acknowledge. Errors retry with capped backoff and are visible through `storageRenewalStatus` (pending/leased/failed counts, oldest pending age, last error) on the list/detail screens. Carried-over P04 revisions without a confirming command cannot authorize postings and are not enqueued until a brand-setup save records an authorized revision.

## Not done here

No P20 payroll, P21 adjustments/openings, P22 orchestration, P23 export pages or P24 profit page. No agreement restart after a stop (a later decision/phase). P04's `storage.active` flag still gates stored-stock pricing as before; storage arrears never block shipping.
